# BharatData API — Blueprint

Status: BLUEPRINT ONLY (built 2026-11-08 on Khushi's request to compare).
CSV Doctor remains the confirmed flagship until Khushi explicitly decides
otherwise after reading this. Nothing here replaces it yet.

---

## 1. What it is (one line)

India's government data exists but is unusable. BharatData automatically
fetches it from official sources, cleans it, versions it, and republishes
it as (a) beautiful searchable dataset pages for humans and (b) a clean,
documented, free API for developers — under the Government Open Data
License – India (GODL), with full attribution.

Tagline candidates: "India's open data, actually open." / "data.gov.in,
cleaned."

## 2. The problem (why this is a real-user product)

Verified facts about the source (checked 2026-11-08):
- data.gov.in (OGD Platform India) is the single-point access to datasets
  published by ministries/departments of the Government of India and
  houses 230,000+ datasets, many updated regularly, with API access.
- Datasets are legally reusable: GODL grants a worldwide, royalty-free,
  non-exclusive licence to use, adapt, publish and create derivative
  products/services for lawful commercial and non-commercial purposes,
  conditioned on attribution and non-endorsement.
- Access pattern is real but painful: every dataset is a separate
  "resource" with its own UUID, fetched as
  `https://api.data.gov.in/resource/<resource-id>?api-key=<KEY>&format=json&limit=<n>&offset=<n>`
  with `filters[field]=value` support. The free sample key returns max 10
  records; a personal key (free, via portal login > My Account) is needed
  for real use. Formats: json / xml / csv.

The pain, concretely, for the 4 user types:
1. **Developers** building India apps (mandi prices, AQI, fuel, trains of
   data): must register, find resource UUIDs, discover each dataset has
   different column names/casing, values stored as strings, dates in 5
   formats, states spelled 4 ways. Every dev rebuilds the same cleaning.
2. **Data-science students / Kaggle users**: want a clean CSV in one
   click; instead get raw dumps with merged headers, footnotes inside
   cells, and no schema.
3. **Journalists / researchers**: need *history* — what did this dataset
   say last month? The portal overwrites; nobody keeps snapshots.
4. **Analysts in small orgs**: need the same 10-20 datasets refreshed
   weekly into Excel/Sheets; they do it by hand.

BharatData's answer to each: one consistent API, cleaned downloads,
versioned snapshots, and refresh done by machines, not people.

## 3. What the user actually gets (product surface)

### 3a. Dataset pages (for humans + Google)
One page per dataset, e.g. `/datasets/daily-mandi-prices-agmarknet`:
- What it is, in 2 plain sentences (never a copy of the official blurb)
- **Live preview table** (first 100 cleaned rows), filterable
- **Charts that matter** for time-series (auto-generated, honest axes)
- Download: clean CSV / JSON / Parquet, one click, no login
- **Data Quality Score** (see §6 — this is where the CSV Doctor engine
  lives inside this product) with the list of what was fixed
- Freshness badge: last fetched, last changed at source, update schedule
- Snapshot history: download *any past version*, diff summary
- Citation box: ready-to-paste attribution (GODL requirement, done for
  the user)
- "Get this via API" code snippet (Python + curl) auto-filled

### 3b. Public API (for developers)
Base: `https://api.bharatdata.<domain>/v1`
- `GET /datasets` — search + filter by sector, ministry, state, freshness
- `GET /datasets/{slug}` — metadata, schema, quality report
- `GET /datasets/{slug}/rows?state=UP&from=2024-01-01&limit=1000`
  — cleaned rows as JSON, consistent types, pagination by cursor
- `GET /datasets/{slug}/rows.csv` / `.parquet` — bulk download
- `GET /datasets/{slug}/snapshots` — version list + download links
- Free API key by email signup; **generous free tier**: 1,000 calls/day,
  rate-limited per key, responses Redis-cached (most calls never touch
  the database)
- OpenAPI docs page (auto-generated by FastAPI) + Postman collection

### 3c. Alerts (Phase 2, the retention hook)
"Email me when this dataset updates / when AQI in my city crosses 300 /
when mandi price of onion in my state moves >10%." Alerts are why users
return without remembering you exist.

## 5. Architecture (on the Oracle VM — reuses the CSV Doctor deploy stack)

Same shape as the automation already built on 2026-11-08
(docker-compose + Caddy + GitHub Actions push-to-deploy). New services in
**bold**:

```
Internet
  └─ Caddy (HTTPS, routing)
       ├─ web/        Next.js — dataset pages (SSG/ISR: pages are static
       │                until a snapshot changes → Google-fast)
       ├─ api/        FastAPI — public API + key auth + rate limits
       │                └─ Redis (cache + rate-limit counters + queues)
       ├─ **ingest/** Celery workers + **Beat scheduler**
       │                per-dataset connectors → raw zone → clean zone
       ├─ **store/**  Postgres (catalogue, users, keys, snapshots meta)
       │              + Parquet files on disk (the data lake; DuckDB
       │              queries them in place — no second database)
       └─ **search/** Postgres FTS for MVP; Meilisearch only if needed
```

Key design decisions (and why — these are interview answers):
- **Raw zone is immutable.** Every fetch is stored byte-for-byte with
  timestamp + source hash before any cleaning. If a cleaning rule is
  wrong, re-clean from raw — never re-fetch history that may be gone.
- **Snapshots = content hashes.** A new snapshot is created only when
  the cleaned data actually changed (hash diff), not on every fetch.
  Storage stays tiny and "what changed" is a real diff, not noise.
- **Parquet + DuckDB over loading everything into Postgres.** Analytical
  queries (aggregations over millions of rows) are DuckDB's strength;
  Postgres keeps what it's best at: catalogue, users, keys.
- **API responses cached by (dataset, snapshot, query) in Redis.**
  Public data changes slowly; cache hit rate will be >95%, so a single
  small VM serves far more traffic than it should be able to.
- **Connectors are config + small code.** Each dataset = one YAML
  (source, schedule, resource id, expected schema) + one clean()
  function. Adding dataset #21 is hours, not days.

## 6. The CSV Doctor connection (why prior work is NOT wasted)

The cleaning layer IS a data-quality product. BharatData reuses, as its
internal QC stage, the exact engine already built for CSV Doctor:
parse (type inference, IDs stay IDs) → profile → deterministic Health
Score → facts pack. Every dataset page publishes that Health Score and
the "what we fixed" list (types coerced, state names normalised to a
canonical list, dates parsed to ISO, duplicates dropped, unit fixes
documented per dataset).

Positioning consequence: CSV Doctor = quality engine for *your* file.
BharatData = quality engine applied to *the nation's* files, in public,
where everyone can see the before/after. The engine gets a showcase;
the showcase gets a moat (nobody trusts a raw mirror).

## 7. Trust, licence, legality

- All OGD data republished under **GODL – India** with attribution on
  every page + in API responses (`source`, `licence`, `attribution`
  fields are part of the schema, not a footer afterthought).
- Non-endorsement: pages state clearly "Not a Government of India
  product; data sourced from OGD Platform India."
- No personal data: datasets are aggregate/official statistics; the MCA
  sampler excludes any personal fields by design.
- API keys can be revoked; per-key rate limits + a fair-use page exist
  from day 1 (abuse management is cheaper designed-in than retrofitted).
- robots/ToS: use official APIs and published downloads only — no
  scraping of the portal's HTML. (This is a design rule, not a hope.)

## 8. Traffic plan (how real users actually arrive)

1. **SEO is the engine.** Every dataset page targets a real query:
   "[dataset] csv download", "[x] data by state", "[x] api". 20 pages at
   launch → 100+ pages as state/sector landing pages are generated
   ("AQI data for Delhi", "mandi prices in UP") from the same data.
2. **Developer channels:** launch posts on r/developersIndia,
   r/india, dev.to ("I cleaned data.gov.in so you don't have to — free
   API"), Hacker News Show HN if the API story is crisp.
3. **LinkedIn build-in-public** (Khushi's existing channel): weekly
   "Dataset of the week" post with one chart nobody else publishes
   (the chart links back to its dataset page).
4. **Kaggle/GitHub spillover:** publish 3-4 cleaned datasets on Kaggle
   with BharatData attribution + API link in the notebook.
5. Month-1 honest targets: 500 dataset-page visits, 50 API keys issued,
   20 repeat API users, 5 inbound dataset requests. Requests are gold:
   they tell you datasets #21-25.

## 9. Build plan (~24 working days, December — after Nov deadlines)

Nov is blocked (Quiz 1 Nov 15, MAD II Nov 17, DL cutoff Nov 18, report
Nov 30). This plan assumes December start, same as CSV Doctor's did.

- **Days 1–2 — Foundations:** repo, docker-compose (copy the proven
  CSV Doctor stack), Postgres schema, source registry YAML format,
  data.gov.in personal API key (free, portal login).
- **Days 3–5 — Ingestion core:** fetcher with offset/limit pagination,
  retries + backoff, raw-zone storage with hashes, Celery + Beat wiring,
  run-log table + admin page (a failed fetch must be visible, not silent).
- **Days 6–8 — Cleaning framework:** wire CSV Doctor parse/profile/score
  as a library; canonical state/district lists; date/number coercers;
  per-dataset clean() contract + golden tests (input raw → expected
  clean) for every connector. No connector ships without a golden test.
- **Days 9–12 — First 5 datasets end-to-end:** mandi prices, AQI, fuel
  prices, rainfall, pincode. Snapshot + diff engine.
- **Days 13–15 — Public API:** datasets/rows endpoints, API keys,
  Redis cache + rate limit, OpenAPI docs polish, Python usage examples.
- **Days 16–19 — Website:** dataset page template (table preview,
  charts, quality report, downloads, citation box), search, home +
  sector pages, sitemap + structured metadata for SEO.
- **Days 20–21 — Datasets 6–20** in batches (files-based ones are fast;
  API ones reuse the Day 3 fetcher).
- **Day 22 — Deploy to the VM:** GitHub Actions (already built),
  domain + HTTPS via Caddy, uptime + fetch-failure alerts to email.
- **Day 23 — Launch content:** dev.to + Reddit posts, first LinkedIn
  "Dataset of the week", Kaggle dataset #1.
- **Day 24 — Buffer / fixes from real first users.**

Phase 2 (January, only if Month-1 targets hit): alerts (§3c),
state/sector landing-page generator, API usage dashboard, webhooks on
dataset update, Hindi UI for dataset pages.

Explicit non-goals for MVP: user uploads (that's CSV Doctor), charts
beyond auto time-series + bar, any paid tier, mobile app, scraping
non-OGD sources.

## 10. Metrics that decide "continue or kill"

- API keys issued and **7-day repeat callers** (the core metric — one
  developer integrating = a user acquired permanently)
- Dataset pages indexed by Google + top-10 queries (Search Console)
- Snapshot freshness: % of datasets fetched on schedule (target 100%;
  a stale data product is a lying product)
- Inbound dataset requests per week (demand signal for expansion)
Kill criteria (honest): if after 60 days and 30 datasets there are
<10 repeat API users and <1,000 organic visits/month, the API bet is
wrong — the asset (pipelines + cleaned lake) still converts into
portfolio + Kaggle content, so the loss is bounded.

## 11. Risks (stated, with mitigations)

| Risk | Reality | Mitigation |
|---|---|---|
| Source data is filthy/inconsistent | Certain | That's the product. Cleaning + quality scores are the value; golden tests stop silent corruption |
| Source stops updating a dataset | Common | Freshness badges show it publicly; never fake freshness; archive mode for dead datasets |
| data.gov.in API rate limits / downtime | Known (sample key capped at 10 records; personal key required) | Own key, patient pagination, backoff, cache raw forever — re-fetches are rare |
| "Why not just use data.gov.in?" | Fair question | Answer = cleaning, history, one consistent API, quality proof. If a user can't feel the difference in 30 seconds on a dataset page, the page failed |
| Traffic is slow | Admitted upfront | SEO compounds; judge at day 60, not day 7. Meanwhile it's a placements asset from day 1 |
| Single VM = single point of failure | True | Nightly backup of Postgres + Parquet lake to object storage / a second free bucket; redeploy is one compose command |
